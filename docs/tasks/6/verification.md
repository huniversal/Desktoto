# #6 사용량 수집 동등성 검증

## 환경과 방법

- 수행일: 2026-11-02, 한국 시간.
- macOS 27.0.1, Xcode 27.1 (27A9275).
- 설치 앱 버전: Claude 4.4212.0, Codex 26.1027.51404.
- 원본의 경로 탐색 순서로 선택한 실행 파일: codex-cli 0.166.0-alpha.5.1.
- 원본 `UsageWatcher.swift`, `ClaudeDesktopUsage.swift`, `CodexRateLimitReader.swift`, `LogTail.swift`를 수정 없이 임시 패키지에 심볼릭 링크로 연결했다. 원본은 Swift 5 모드, 새 Domain, Boundaries, UsageMonitoring은 Swift 6 모드로 컴파일했다.
- 임시 비교 패키지는 `/tmp/desktoto-usage-verify`에 두었다. 원본 앱과 새 앱을 설치하거나 실행하는 대신 원본 수집 함수를 같은 Mac에서 직접 호출했다.
- 파일 수집은 고정된 now로 비교했다. 원본 데스크탑 탐색은 동기 모드로 수행하고, 새 수집기의 백그라운드 탐색 완료를 기다린 뒤 비교했다.
- statusLine은 양쪽 모두 데스크탑 캐시를 제외한 별도 조회로 비교했다. 데스크탑 캐시는 원본의 원시 스냅샷에 초기화 보정을 적용한 값과 새 수집기의 statusLine 제외 결과를 비교했다.
- 실시간 조회는 원본과 새 수집기가 각각 설치된 codex의 `account/rateLimits/read`를 호출했다. 인증 정보나 HTTP API를 비교 도구에서 직접 읽거나 호출하지 않았다. 종료 시 두 수집기 모두 stop을 호출했다.
- 개인 로그와 사용량 원문은 저장하거나 출력하지 않았다. 출력에는 소스 가용 여부와 항목별 일치 여부만 남겼다. 테스트에는 실제 파일을 사용하지 않았다.

## 결과

| 대상 | 양쪽 가용 | 사용 비율 | 초기화 시각 | 수신 시각 |
| --- | --- | --- | --- | --- |
| Claude 데스크탑 캐시 | 예 | 두 한도 일치 | 두 한도 일치 | 파일 수정 시각 일치 |
| Claude statusLine | 예 | 두 한도 일치 | 두 한도 일치 | 파일 수정 시각 일치 |
| Codex 세션 기록 | 예 | 두 한도 일치 | 두 한도 일치 | 기록 timestamp 일치 |
| Codex 실시간 응답 | 예 | 두 한도 일치 | 두 한도 일치 | 각 응답 수신 시점으로 생성, 동일 시각 비교 제외 |
| 도구별 최신값 선택 결과 | 예 | 일치 | 일치 | 파일 소스 비교 시 일치 |

여기서 두 한도 일치는 한도가 없는 경우 양쪽 모두 nil인 것도 포함한다.

첫 비교에서는 원본 조회 후 약 2초 뒤의 새 조회를 비교하여 Codex 기록 결과가 달랐다. 이후 원본과 새 수집기를 연속으로 조회한 세 번의 비교에서 사용 비율, 초기화 시각과 기록 시각이 모두 일치했다. 현재 작업 세션의 기록이 갱신되는 환경이므로 실제 비교는 고정 now뿐 아니라 읽는 파일의 갱신 시점도 맞춰야 한다.

## 자동 검증

- `cd apps/macos`에서 `swift build`: 성공, 최종 로그에 경고 없음.
- `swift test`: 전체 151개 통과. UsageMonitoringTests 25개 포함.
- 경계 테스트: 탐색 600개 제한과 크기 필터, 120초 재탐색, 4MiB까지 로그 확대 읽기, 캐시 무효화, zstd 1MiB 경계, 타임아웃, 재시도, 취소, 종료, 유휴 정리, 잘못된 초기화 결과와 콜백 대기 중 통신.
- 임시 폴더의 파일 정보와 실제 `/bin/cat` 프로세스의 입력, 출력, 종료도 검증했다.

## 검증 범위의 한계

이 결과는 현재 설치 환경의 수집 계층 동등성 확인이다. 두 앱의 화면을 나란히 실행한 전체 제품 동등성 확인은 아니다. UI와 타이머, 설정 연결은 #10과 #11 이후에 검증한다.
실제 환경의 권한 거부, 네트워크 단절, 외부 앱의 미래 형식 변경을 재현하지 않았다. 파일 누락과 형식 오류, 실패 후 대체, 요청 제한 시간, 취소는 가짜 구현과 합성 데이터로 검증했다.


## 리뷰 후 응답 순서 보완

- 서브에이전트 리뷰에서 read 응답 뒤의 갱신 알림이 이전 응답으로 덮이거나, 응답 직후 EOF로 성공 값이 버려지는 P2 결함을 합성 입력으로 각각 5회 확인했다.
- `CodexRateLimitReader`가 응답 종류를 추적하고 수신 처리 안에서 값 저장, 요청 완료와 유휴 종료 예약을 끝낸 뒤 continuation을 재개하도록 수정했다. 이전 refresh가 뒤늦게 값을 저장하지 않는다.
- `ResponseOrderingTests` 두 개로 응답 10%와 후속 알림 60%가 같은 조각인 경우 최종 60% 유지, 응답 10% 직후 EOF인 경우 10% 보존을 검증했다.
- 수정 후 `swift build` 성공, 전체 테스트 151개 통과, 실제 네 소스의 원본 비교도 다시 일치했다.
