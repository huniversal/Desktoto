# 작업 명세: [Feat] 앱 내 새 버전 알림

## 연결 정보

- 이슈: #24 / https://github.com/huniversal/Desktoto/issues/24
- 브랜치: feat/update-notice/#24
- specRevision: 1
- 대상 ai-run 원본: N/A (원본에 없는 새 기능이다)

## 목적

Homebrew나 릴리스 zip으로 설치한 사용자가 새 버전이 나온 것을 알 수 있게 한다. Homebrew는 사용자가 직접 명령을 실행해야만 갱신하므로, 알림이 없으면 새 버전이 나온 줄 모른다.
앱이 시작할 때 최신 릴리스를 확인하고, 현재 버전보다 높으면 우클릭 메뉴에 안내 항목을 보여 준다. 안내 문구는 설치 방식에 따라 갱신 방법(`brew upgrade`나 릴리스 페이지)을 알려 준다.

앱이 외부 네트워크에 접근하는 첫 기능이다. 사용자 정보나 세션 내용은 보내지 않고 최신 릴리스 정보를 읽기만 한다.

## 작업 범위

### 포함

- GitHub Releases의 최신 정식 릴리스를 읽는 확인 로직. 네트워크 접근은 외부 경계(프로토콜)로 분리해 테스트에서 대체한다.
- 현재 앱 버전과 최신 태그의 비교를 순수 함수로 분리하고 단위 테스트 작성(형식 오류 포함).
- 확인 시점과 주기: 시작할 때 한 번, 그 뒤 24시간마다. 오프라인과 요청 제한 같은 실패에서는 조용히 넘어간다.
- 우클릭 설정 메뉴에 새 버전이 있을 때만 "새 버전이 있어요" 항목 추가. 누르면 릴리스 페이지를 연다. 안내 문구는 설치 방식(Homebrew 여부)에 따라 다르다.
- 업데이트 확인을 끌 수 있는 설정 항목("업데이트 확인")을 추가한다. 기본값은 켜짐이다.
- 새 모듈 `UpdateCheck` 추가와 [아키텍처](../../architecture.md) 문서 갱신. 같은 문서에 #29 이후 어긋난 Claude 연동 기본값 문장을 정정한다.
- 실제 Mac에서 새 버전 있음, 없음, 오프라인, 설정 끔 동작 확인과 문서 갱신.

### 제외

- 앱 안에서 내려받고 교체하는 자동 업데이트(Sparkle)
- Apple Developer 서명과 공증
- 프리릴리스 알림(정식 릴리스만 알린다)

## 설계 결정

- 파일 구조와 로직의 책임:
  - 새 기능 모듈 `UpdateCheck`(`apps/macos/Sources/UpdateCheck/`, 의존은 `Boundaries`)를 둔다. 한 기능만 쓰는 서비스는 그 기능 모듈 안에 둔다는 [아키텍처](../../architecture.md) 5장 원칙을 따른다.
  - 순수 값과 함수: `AppVersion`(`1.2.3` 형식 해석과 비교), 갱신 안내 값(새 버전 번호, 릴리스 페이지 주소, 갱신 방법).
  - 경계: 최신 릴리스 조회 프로토콜(`Sendable`)과 `URLSession` 기반 실제 구현. 테스트는 가짜 구현을 주입한다.
  - 확인 주기 판단은 `TimeSource`로 현재 시각을 주입받아 테스트한다.
  - `Preferences`는 설정 항목(`checksForUpdates`)과 메뉴 항목 모델만 맡는다. 모듈끼리 서로 import하지 않고 조립은 `Desktoto`가 한다.
- 상태와 데이터 흐름: 시작 때와 24시간 타이머 때 `Desktoto`가 확인을 요청하고, 결과(새 버전 있음 또는 없음)를 메뉴를 만들 때 환경 값으로 넘긴다. 마지막 확인 시각은 메모리에만 둔다(영속하지 않는다).
- 선택한 방식과 이유:
  - 최신 릴리스는 GitHub API `releases/latest`로 읽는다. 프리릴리스와 초안을 자동으로 제외해 tap이 프리릴리스를 건너뛰는 것과 일치한다. 인증 없이 시간당 60회 제한이라 24시간 주기에 충분하다.
  - 응답은 미검증 입력이다. 태그가 `v숫자.숫자.숫자` 형식일 때만 받아들이고, 열 주소는 응답의 URL이 아니라 앱이 태그로 직접 만든 `https://github.com/huniversal/Desktoto/releases/tag/<태그>`를 쓴다.
  - 현재 앱 버전은 번들의 `CFBundleShortVersionString`에서 읽는다. 앱(`.app`)이 아니면(`swift run`) 버전을 알 수 없어 확인하지 않는다.
  - 설치 방식은 `Caskroom/desktoto` 폴더 존재로 판별한다(`/opt/homebrew`와 `/usr/local` 두 위치). 첫 릴리스 후 실제 `brew install`로 확인하기 전까지는 가설이다.
- 예외 처리: 오프라인, 시간 초과, HTTP 403과 429(요청 제한), 404(릴리스 없음), 형식 오류는 모두 "새 버전 없음"으로 처리하고 앱 동작에 영향을 주지 않는다. 실패해도 재시도를 쌓지 않고 다음 주기까지 기다린다. 확인이 겹치지 않게 진행 중이면 새로 시작하지 않는다.

## 완료 조건

- AC-1: 버전 비교가 순수 함수로 분리되어 있고, `1.9.0`과 `1.10.0`의 숫자 비교, 같은 버전, 더 낮은 버전, 형식 오류(`v` 접두사 유무, 자리 수 부족, 문자 포함)를 단위 테스트가 검증한다.
- AC-2: 최신 릴리스 조회는 프로토콜 뒤에 있고 가짜 구현으로 테스트된다. 태그 형식이 올바르지 않은 응답은 무시한다.
- AC-3: 시작할 때 한 번 확인하고 그 뒤 24시간마다 확인한다. "업데이트 확인"이 꺼져 있으면 네트워크 요청을 하지 않는다.
- AC-4: 오프라인, 시간 초과, 403, 429, 404, 형식 오류에서 "새 버전 없음"으로 처리하고 앱이 멈추거나 오류 창을 띄우지 않는다.
- AC-5: 새 버전이 있을 때만 우클릭 메뉴에 "새 버전이 있어요 (v버전)" 항목이 보이고, 누르면 릴리스 페이지가 열린다. 설치 방식이 Homebrew면 `brew upgrade --cask desktoto` 안내가 함께 나온다.
- AC-6: 설정 메뉴에 "업데이트 확인" 항목이 있고 기본값은 켜짐이다. 끄면 저장되고 재시작 후에도 유지되며, 안내 항목이 사라진다.
- AC-7: `Package.swift`, `docs/architecture.md`(모듈 표, 의존 방향, 외부 경계)가 `UpdateCheck` 모듈을 반영하고, 같은 문서의 Claude 연동 기본값 문장이 현재 동작(첫 실행에서 켜짐)과 일치한다.
- AC-8: 실제 Mac에서 새 버전 있음, 없음, 오프라인, 설정 끔 동작을 확인하고 결과를 기록한다.

## 미결정 사항

- Homebrew 설치일 때 항목을 눌렀을 때의 동작: 릴리스 페이지를 열지, `brew upgrade --cask desktoto`를 클립보드에 복사할지. 구현 전에 정한다. 구현을 막지 않는다.
- `Caskroom/desktoto` 폴더로 Homebrew 설치를 판별하는 방식이 실제 설치에서 맞는지는 첫 릴리스 후 확인한다. 막지 않는다.
- AC-8의 "새 버전 있음" 확인은 릴리스가 둘 이상 생겨야 가능하다. 첫 릴리스 전에는 가짜 응답을 쓰는 테스트로만 검증하고, 실제 확인은 두 번째 릴리스 이후로 미룬다.
- 새 기능이라 원본 ai-run에 대응하는 동작이 없다. `docs/reverse/`의 "원본과 달라진 점"에 기록할지는 구현 때 정한다.
