# Git, 커밋, PR 컨벤션

저장소 전체의 공통 기준이다. Keeply의 Git Flow와 type 기반 커밋 방식을 따르고,
Ttak에서 합의한 형식을 Desktoto에 맞췄다.

## 브랜치와 흐름

| 브랜치 | 역할 | 경로 |
| --- | --- | --- |
| `main` | 배포 기준 | 배포 시 develop → main PR |
| `develop` | 개발 통합, 기본 브랜치 | 작업 브랜치 → develop PR |
| `feat/작업명/#이슈번호` | 작업 브랜치 | 최신 develop에서 분기 |

- 사용자가 다른 이름의 브랜치를 지정하면 따른다.
- `#`가 포함된 브랜치 이름은 셸에서 작은따옴표로 감싼다.
- `main`, `develop`에 직접 구현하거나 push하지 않는다. 모든 변경은 PR로 병합한다.
- 병합은 Merge commit 방식을 사용한다.
- 배포 후 필요한 main → develop 동기화도 PR로 진행한다.
- 기본 브랜치는 하네스 커밋까지 끝난 뒤 `develop`으로 바꾼다.

## 커밋 메시지

형식은 소문자 `type: 설명`이다. type은 영어, 설명은 한국어로 작업 목적이 드러나게 쓴다.
본문이 필요하면 빈 줄 뒤에 이유와 영향을 적고, 이슈 참조는 `Refs #번호`로 연결할 수 있다.
모든 커밋 제목에 이슈 번호를 강제하지 않으며, 이미 있는 커밋을 소급해서 다시 쓰지 않는다
(단, push 전의 로컬 커밋은 예외).

| type | 사용 기준 |
| --- | --- |
| `feat` | 새 기능 |
| `fix` | 잘못된 동작 수정 |
| `docs` | 문서만 변경 |
| `refactor` | 외부 동작을 유지하는 코드 구조 개선 |
| `style` | UI 표현, 디자인 변경 (동작 결함 수정은 fix) |
| `test` | 테스트 추가와 수정 |
| `chore` | 하네스, 빌드, 의존성, 설정, 유지 관리 |
| `perf` | 성능 개선 |

예:

```text
feat: 세션 감시 로직을 별도 모듈로 분리
fix: 로그 파일이 잘렸을 때 파싱이 멈추는 문제 수정
docs: SessionWatcher 동작 문서화
chore: 프로젝트 초기 세팅
```

커밋 하나는 설명할 수 있는 목적 하나로 구성한다. 사용자 변경이나 미검토 파일을 함께 스테이징하지 않는다.

## 이슈

- 제목 형식은 `[Type] 설명`이다. 예: `[Feat] 세션 감시 모듈 구현`.
- `부터`, `까지` 같은 연결 표현을 피하고 `및` 등으로 간결하게 쓴다.
- 본문은 [이슈 템플릿](../../.github/ISSUE_TEMPLATE/issue_template.md)을 따른다.

## PR

- 제목 형식은 `Type: 설명`이다. 예: `Feat: 세션 감시 모듈 구현`. 이슈 제목(`[Type] 설명`)과 구분한다.
- [PR 템플릿](../../.github/pull_request_template.md)으로 변경 내용, 검증, 관련 이슈를 설명한다.
- 이슈 전체를 완료하면 `Closes #번호`, 일부 작업이면 `Refs #번호`를 쓴다.
- 실제로 실행한 검증과 실패, 미실행, 환경 한계를 적는다.
- 출발과 대상 브랜치, Merge commit 방식을 확인한다.
- 작게 만들고 일찍 올린다. 1인 프로젝트이므로 다른 사람의 승인 대신 자기 검토와 검증 기록을 남긴다.

## 라벨

GitHub 저장소에 만들어 둔 이름을 그대로 쓴다. 같은 뜻의 중복 라벨을 만들지 않는다.

| 라벨 | 용도 |
| --- | --- |
| `FEAT` | 새 기능 |
| `FIX` | 버그 수정 |
| `DOCS` | 문서 |
| `REFACTOR` | 구조 개선 |
| `STYLE` | UI, 디자인 |
| `CHORE` | 유지 관리, 도구, 설정 |
| `TEST` | 테스트 |
