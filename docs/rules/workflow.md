# 작업 흐름

이슈 → 작업 브랜치 → docs 작업 정의 → 개발 → 검증 → PR 순서로 진행한다.
읽기 전용 조사, 설계, 리뷰는 이슈나 작업 브랜치가 없어도 가능하다.
코드 변경은 [공통 컨벤션](coding-convention.md)과 [Swift 컨벤션](swift-coding-convention.md)을,
브랜치, 커밋, PR은 [Git 컨벤션](git-convention.md)을 읽고 적용한다.

## 단계

1. **이슈**: [이슈 템플릿](../../.github/ISSUE_TEMPLATE/issue_template.md)으로 만든다. 이슈 생성 요청은 이슈만 만들고 구현으로 넘어가지 않는다.
2. **브랜치 생성**: 최신 `develop`에서 `feat/작업명/#이슈번호`로 분기한다.
3. **docs 작업 정의**: `docs/tasks/이슈번호/spec.md`를 [템플릿](../tasks/_template/spec.md)으로 작성하고,
   개발 전에 `docs: 이슈번호 작업 명세 추가` 형태로 커밋한다.
4. **개발**: 명세의 포함 범위만 구현한다. 작은 단위로 커밋한다.
5. **검증**: 명세의 완료 조건(AC)과 검증 표대로 확인한다. 실제 실행 결과를 PR에 적는다.
6. **PR**: 대상은 `develop`이다. 이슈를 완료하면 `Closes`, 일부면 `Refs`를 쓴다.

## 명세 규칙

- 위치는 `docs/tasks/이슈번호/spec.md`이다.
- 완료 조건은 고유한 `AC-N`으로 적고, 검증 표에서 각 AC의 확인 방법을 정한다.
- 구현 중 합의가 바뀌면 `specRevision`을 올리고 변경 이유와 영향받는 AC를 "주요 설계 변경"에 남긴다.
- 사용자와 합의하지 않은 내용을 확정 요구사항으로 쓰지 않는다. 제안과 일반 질문은 결정이 아니다.
- 리버스 엔지니어링 작업의 명세에는 대상 `ai-run` 원본 파일과 문서화 위치(`docs/reverse/`)를 적는다.

## 예외

- 오타나 1파일 5줄 이하의 사소한 수정은 이슈와 명세를 생략할 수 있다. 시작 전에 생략한다고 선언한다.
- 하네스와 문서 전용 작업은 앱 빌드 검증을 N/A로 하고 이유를 PR에 적는다.

## 변경별 검증

| 변경 | 검증 |
| --- | --- |
| 문서, 스킬 | 링크와 정책 점검, diff 검토. 앱 빌드는 N/A |
| Swift 소스 | `swift build`, 테스트가 있으면 `swift test`, 변경 기능의 실제 실행 확인 |
| 외부 연동, 파일 접근, 알림 | 위 검사와 실제 Mac에서 동작, 실패, 재시도 확인 |
| 동등성 | 기존 ai-run과 나란히 실행해 기능 체크리스트로 대조 |

## 리뷰와 게시

- 리뷰는 커밋, staged, unstaged, 새 파일을 모두 포함하고 관련 호출부만 추가로 읽는다.
- 기준은 이슈의 완료 조건, 상태와 비동기 수명, 오류와 취소, 외부 입력 검증, 기존 기능 영향이다.
- 지적은 심각도, 파일, 줄, 영향, 수정 방향을 기록한다. 미해결 High와 Medium이 있으면 게시하지 않는다.
- 리뷰를 요청받았다고 서브에이전트를 실행하지 않는다.
- 환경 제약이 있으면 원인을 보고한다. 미검증 상태의 게시는 사용자가 명시적으로 요청한 경우에만 하고, 통과로 표시하지 않는다.
- GitHub 설정과 CI는 명시적인 작업 범위에서만 변경한다.
